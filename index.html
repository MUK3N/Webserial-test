Wiring

USB-to-TTL serial adapter, three wires, no driver install needed beyond what Chrome already handles.

Connections

TX ↔ RX, RX ↔ TX, GND ↔ GND. The two TX/RX lines are crossed — the adapter's TX goes to the sensor's RX, and vice versa.

If the sensor doesn't respond to anything once connected, it's most likely asleep — restart it with the magnet before troubleshooting the wiring.

The magnet

Hold it to the sensor's marked spot, then remove it — that's a restart. It's used twice in a normal session: once to enter debug mode for reading credentials, and once more afterwards to put the sensor back into its normal 115200 mode.

Browser & hosting

This page talks to the sensor directly from your browser — nothing passes through a server.

Requirements

Web Serial only works in Chrome, Edge or Opera, and only over HTTPS or http://localhost — it won't appear at all in Firefox/Safari or over plain HTTP.

All device communication happens locally in your browser tab. Nothing you read from or send to the sensor is uploaded anywhere by this page.

Reading LoRaWAN credentials, step by step

Every step here is a button press on purpose — the sensor's own baud-rate switch takes a variable amount of time, so each step waits for you to see it happen rather than guessing.

The five clicks
  1. Read Credentials — starts sending "@" to the sensor, asking it to enter debug mode.
  2. Tap the magnet, then click "I restarted it with the magnet — continue." Don't click this before you've actually tapped the magnet — see the warning below.
  3. Send "3" — tells the sensor to enter debug mode, once you can see its mode-select menu in the raw log.
  4. Reopen at 9600 — click once the sensor is visibly prompting for the baud switch. This reopens the connection on the browser side to match.
  5. Send AT+ID — reads back DevAddr, DevEUI and AppEUI/JoinEUI. If it doesn't catch a clean reply, you can press it again without restarting the whole flow.
If step 2 gets clicked too early

If "continue" gets clicked before the magnet is actually tapped, the sensor never enters its debug menu — so sending "3" afterwards does nothing meaningful. If the flow is then pushed on to "reopen at 9600," the browser switches speed but the sensor doesn't, and from that point nothing readable comes back.

Press Reset (next to Read Credentials) to recover — it reopens the connection at 115200 to resync with the sensor and puts the flow back at the start, no page reload needed.

Writing a new AppKey

AppKey is write-only by design on this module.

Why it can't be read back

There's no AT command that queries a stored AppKey — only one that sets it (AT+KEY=APPKEY,"..."), and the module echoes back exactly what was just written as confirmation, nothing more. This is deliberate hardware/firmware behavior, not a limitation of this page.

Writing one requires debug mode, so run "Read Credentials" first — the field stays locked until that succeeds, and it's cleared from the page the instant it's sent.

Command reference

DF555 Protocol V3.2 — what each field on the Configuration page actually sends.

Downlink-format commandssent at 115200 baud

0x01 upload interval (1–168h) · 0x08 detection interval (1–60min) · 0x09 functions (work mode, tilt, GPS, echo) and sub-command 02 (restart) · 0x02 full threshold · 0x03 fire/temp threshold · 0x04 tilt/fall threshold · 0x05 battery threshold.

Entering AT command mode

Unlike LevelPro, this doesn't need a magnet — it's a handshake the app runs automatically on Connect. The real hardware behavior turned out to differ from the manual's.

What actually worksconfirmed on real hardware

Connect at 8 data bits, 1 stop bit, and whichever baud/parity the unit is actually on — 115200, None for a factory-fresh unit (the manual's own default), or 19200, Even for one that's already been provisioned (confirmed on the units configured so far for this client; a different client's units may end up on a different value after their own provisioning). Pick it in the connection card before clicking Connect. The gateway prints its own continuous boot/status chatter from the moment the port opens, mixed characters with no reliable line breaks — that's normal and happens regardless of anything sent to it. Once baud/parity match the unit, the manual's original handshake shape turns out to be correct after all:

  1. First, send a bare AT and check for a reply ("OK" or any "+CME ERROR") — those only happen in AT mode, so seeing one means the gateway is already there (e.g. an earlier session left it in AT mode and it never left). If so, skip straight to AT mode — no +++ needed.
  2. Otherwise, wait a moment after the connection opens — not an instant +++. The chatter continuing in the background is fine.
  3. Send +++ once.
  4. Watch for a to show up, mixed in with more chatter — confirmed to arrive well under a second later.
  5. Within that same second or so, send a back once.
  6. +ok follows shortly after, mixed into the stream the same way — that's AT command mode.

This app does exactly that automatically on Connect, watching the raw byte stream rather than waiting for a clean line. It sends AT (the already-in-AT-mode check), then +++ and a once each if needed — no spamming — and if a step times out it stops and reports it rather than retrying on its own; click "Enter AT mode" to try again by hand. If you ever see "+CME ERROR:58" right after "+++" instead of "a", that's this exact already-in-AT-mode case, not a wrong baud/parity. To leave AT mode and resume normal MQTT/transparent operation, send AT+ENTM (confirmed in the manual). Disconnecting does this for you.

What's confirmed, what isn't

Be more careful with the fields marked unverified — check the raw log after each one.

Confirmed on real hardware

Connecting at 115200 8N1 (factory-fresh) or 19200 8E1 (already provisioned, this client) · entering AT mode with +++ → wait for a → send a → +ok, matched against the raw byte stream rather than a clean line · exiting with AT+ENTM (manual) · AT+S save & restart (manual) · AT+Z restart without saving (manual) · AT+CLEAR factory reset (manual) · AT+CSQ signal quality (standard on virtually all cellular modems) · AT+IMEI replying +IMEI:<number> then OK. AT+VER is documented in the manual but hasn't actually been seen to reply yet.

From the client's own provisioning SOP

AT+WKMOD=MQTT,NOR (MQTT work mode, sent automatically ahead of any other MQTT field) · AT+MQTTSUBTP/AT+MQTTPUBTP with a leading slot number (1,<qos>,<topic>,<flag>) · AT+MQTTWILL=<slot>,<topic>,<qos>,<retain>,<payload>, replacing the earlier guessed AT+MQTTWILLEN/AT+MQTTWILLTP pair the gateway rejected with +CME ERROR:58. These are copied verbatim from the client's own working procedure rather than the manual or Figma design, but still haven't been sent by this app against real hardware yet — send them one at a time and check the raw log, same as anything else here.

Not yet verified on hardware

AT+UART (serial settings), AT+MQTTSVR/MQTTCID/MQTTUSER/MQTTPSW (broker), AT+APN (cellular), and AT+MQTTSTA (broker status) are the command names shown on this screen's design — the parameter order, and the gateway's reply format for all of them, haven't been checked against real hardware yet. Given the manual was already wrong about the connection baud and the handshake, treat its documented syntax for these as a starting guess too, not a guarantee.

Change one field at a time, send it, and read what comes back in the raw log — that's how LevelPro's commands went from "design preview" to confirmed, too.
